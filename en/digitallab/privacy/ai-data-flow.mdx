This page details the categories of data generated by the AI assistant, how they are stored, what a request consists of, and the conditions under which data leaves the local machine. Content is based on the v1.6.0 code.

<Note>
  The AI assistant is currently in conversational mode and **does not include Agent tool calling capability**: requests do not carry tool definitions, and models cannot call local tools. `core/agent_tools.py` in the repository is not currently exposed to the model.
</Note>

## Information collected (AI-related)

DigitalLab collects or generates the following AI-related information on the local machine.

### AI conversation history

Conversation content between you and the AI assistant (generated only when you actively use the AI feature). Saved by default to the local file `%APPDATA%\DigitalLab\memory\chat_history.jsonl` and restored after restart; the Chat History section in the Settings panel lets you toggle saving, set a retention limit (20 to 5000, default 200; oldest entries are trimmed beyond it) or clear everything at once.

- Turning off "Save chat history" only stops new messages from being written to that local file; it does not delete existing records (clear them or delete the file manually).
- Turning off "Save chat history" does not stop AI requests: the message you send now and the conversation content already in the session are still sent to the selected AI service with this request.
- The chat history file itself is never uploaded as a whole to any server.

### AI memory (optional, off by default)

Only after you enable memory in Settings, preferences you explicitly expressed and that are worth remembering long-term (such as how you are addressed, device names, usage habits) are persisted in `%APPDATA%\DigitalLab\memory\ai_memory.jsonl`.

- **Writing**: content bearing memory tags in the model reply is extracted, up to 3 entries per reply, each up to 500 characters; memory tags are always removed from the displayed reply, but are only written to the file when memory is enabled.
- **Injection**: when memory is enabled, the most recent 10 entries are injected into every request, each truncated to 200 characters.
- **Condition for leaving the local machine**: when memory is enabled and a remote model is used, the injected memory content is sent to that service with the request.
- **After turning off memory**: no new memory is written; the saved memory file is neither read nor injected into the conversation, but the file itself remains on the local machine and must be deleted or cleared in Settings.

### AI request context (created only when the AI feature is used)

The message list assembled by the backend (the `messages` field in the JSON request body, i.e. the model-visible context) contains four parts:

1. **Static prompt**: role definition, usage rules, output format constraints; plus memory instructions when memory is enabled.
2. **Memory content**: only when memory is enabled; the most recent 10 entries, sorted deterministically by time and identifier.
3. **Real-time system status summary**: CPU/memory/disk usage, CPU/GPU/memory/disk model and capacity, configured NAS device names, online state, CPU/memory/disk usage and temperature.
4. **Conversation content**: the message you send now plus the conversation already in the session; the backend keeps only the last 16 messages.

The following information **does not enter the model context**: NAS host addresses and login credentials, the full process list and command lines, log contents, AI memory id/kind/tags/source fields, and the API Key.

**AI memory and chat history are two independent features**: the memory switch controls reading, injection and persistence of long-term memory and is off by default; the history switch controls local chat record writing and is on by default. Turning one off does not turn off the other and does not stop AI requests.

## What a request contains

An AI request consists of an HTTP request header and a JSON request body; the two carry different content:

| Part | Contents | Visible to the model? |
| --- | --- | --- |
| HTTP request header | `Content-Type: application/json`; cloud models also include `Authorization: Bearer <API Key>` | No, used only for server-side authentication |
| JSON request body | `model` (model name), `messages` (the four-part context above), `stream: true` | `messages` is the model context |

The API Key is sent with every cloud request to the endpoint you configured, but appears only in the `Authorization` request header, not in the JSON request body, prompt, system message or conversation content. Requests sent to Ollama do not carry an `Authorization` header.

## Model selection and data destination

| Item | Ollama | Cloud model (OpenAI-compatible API) |
| --- | --- | --- |
| Default address | `http://localhost:11434` (changeable in Settings) | `https://api.deepseek.com` (changeable in Settings) |
| Default model name | `llama3` | `deepseek-chat` |
| Request path | `{base_url}/api/chat` | `{base_url}/v1/chat/completions` |
| Does data leave the local machine? | No when using a local address; if changed to another host, the request goes to that host | Yes, request is sent to the service endpoint you configured |
| API Key | Not sent | Required, sent via `Authorization: Bearer` header |
| AI conversation history storage | Local `chat_history.jsonl` | Same as left; history is always stored locally |
| AI memory storage | Local `ai_memory.jsonl` | Same as left; memory is always stored locally |
| Model context scope | Static prompt, memory (if enabled), real-time system status, last 16 messages of conversation | Same as left |

Both model addresses are subject to the same [AI endpoint transport policy](/en/digitallab/privacy/sensitive-information#ai-endpoint-transport-policy):

- Remote HTTPS is allowed, with default TLS certificate validation; a custom CA can be specified with `ai.ca_bundle`, and requests fail if the file is missing or unreadable.
- Loopback HTTP is allowed.
- Private network and Tailscale addresses for HTTP require precise authorization in `ai.allow_insecure_http` as `ip[:port]`.
- Domain names, public IPs, link-local and cloud metadata addresses for HTTP are all denied.
- Requests do not follow HTTP redirects.

## Request flow

<Steps>
  <Step title="User input">
    You type a message in the AI assistant panel and send it.
  </Step>
  <Step title="Context assembly">
    The backend assembles the model context: static prompt, memory content (if enabled), real-time system status summary, last 16 messages of conversation.
  </Step>
  <Step title="Endpoint check">
    The backend checks the configured address against the AI endpoint transport policy; requests that do not comply fail directly and are not sent.
  </Step>
  <Step title="Send request">
    When using Ollama, the request is sent to the Ollama address you configured (default local `localhost:11434`, where data does not leave the local machine). When using a cloud model, the request is sent to the `base_url` you configured; the API Key is placed in the `Authorization` header and data is processed by that service.
  </Step>
  <Step title="Local recording">
    Conversation content is written to the local `chat_history.jsonl` according to the "Save chat history" switch; when memory is enabled, memory tags in the reply are extracted and written to `ai_memory.jsonl`.
  </Step>
</Steps>
